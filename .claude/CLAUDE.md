# CLAUDE.md

이 리포에서 Claude Code가 지킬 지침. 행동 지침(1~5절)이 기준이고, 리포 고유 규칙은 `.claude/rules/`, 구조·개발 가이드는 `.claude/guides/`에 나눠 둔다.

## 이 리포지토리

SDLC(Software Development Life Cycle) 전체에 걸친 업무 및 관리 솔루션을 만들기 위한 **설계 단계 문서(드래프트)**를 관리하는 워크 리포지토리다. 대상은 요구사항, 시퀀스 다이어그램, ERD, 시스템 아키텍처, 개발 도구, 코드 리뷰, 빌드·배포, 운영이고, 의사 결정 기록도 여기에 남긴다. 문서 안의 YAML·셸·워크플로 코드는 대상 팀 저장소에 적용할 예시이고, 이 리포에서 실행하는 코드가 아니다.

리포 안의 문서를 메뉴 + 뷰어로 관리하는 로컬 웹사이트(`site/`)와, 이를 팀용 서비스로 옮긴 Cloudflare 앱 「문서 탐색 워크플로우」(`apps/worker`, `workflow.simplite.net`)를 만들고 있다. 요구사항, 결정 사항, 단계별 계획은 `spec/REQUIREMENT.md`(1.x), `spec/REQUIREMENT-2.0.md`(2.0: HTML·DOCX·PPTX·XLSX 텍스트 편집), `spec/REQUIREMENT-3.0.md`(3.0: Claude Code 직접 연결), `spec/REQUIREMENT-4.0.md`(4.0: Cloudflare SaaS 전환 설계·단계 계획)에 있다.

## 작업 원칙

- 응답과 문서는 한국어로 쓴다.
- 결과물은 코드보다 설명, 프로세스, 그림, 문서 위주로 만든다.
- 작업 전에 해당 요구사항 문서의 현재 단계와 결정 사항(D-n)을 확인하고, 미결정 항목은 진행하기 전에 묻는다.
- 커밋·푸시는 사용자가 요청할 때만 한다.

## 규칙과 가이드

리포 구성과 기술 선택의 정본은 `spec/ARCHITECTURE.md`, 요구사항·결정은 `spec/REQUIREMENT*.md`, 테스트 케이스는 `spec/TESTING.md`다. 규칙(`.claude/rules/`)은 자동으로 읽힌다. 경로 조건이 있는 규칙은 그 경로의 파일을 열 때 읽힌다. 가이드(`.claude/guides/`)는 해당 영역을 작업하기 전에 직접 읽는다.

| 규칙 | 적용 범위 | 내용 |

# 행동 지침

LLM이 자주 저지르는 코딩 실수를 줄이기 위한 행동 지침.

**트레이드오프:** 이 지침들은 속도보다 신중함에 무게를 둔다. 사소한 작업에는 상황에 맞게 판단한다.

## 1. 코딩하기 전에 생각하라

**가정하지 마라. 혼란을 숨기지 마라. 트레이드오프를 드러내라.**

구현하기 전에:

- 가정을 명시적으로 밝혀라. 확신이 없으면 물어라.
- 해석이 여러 가지라면 모두 제시하라 — 말없이 하나를 고르지 마라.
- 더 단순한 접근법이 있다면 말하라. 정당한 근거가 있으면 반론을 제기하라.
- 무언가 불분명하면 멈춰라. 무엇이 헷갈리는지 짚어라. 물어라.

## 2. 단순함을 우선하라

**문제를 푸는 최소한의 코드. 추측성 코드는 없다.**

- 요청받지 않은 기능은 만들지 마라.
- 한 번만 쓰는 코드에 추상화를 넣지 마라.
- 요청하지 않은 "유연성"이나 "설정 가능성"을 넣지 마라.
- 일어날 수 없는 시나리오에 대한 에러 처리를 하지 마라.
- 200줄을 썼는데 50줄로 가능하다면 다시 써라.

스스로에게 물어라: "시니어 엔지니어가 이걸 보고 과하게 복잡하다고 할까?" 그렇다면 단순화하라.

## 3. 외과적 변경

**꼭 필요한 것만 건드려라. 네가 만든 것만 정리하라.**

기존 코드를 편집할 때:

- 인접한 코드, 주석, 포매팅을 "개선"하지 마라.
- 망가지지 않은 것을 리팩터링하지 마라.
- 네 방식과 다르더라도 기존 스타일을 따르라.
- 무관한 죽은 코드를 발견하면 언급하되 — 삭제하지는 마라.

네 변경이 고아 코드를 만들었다면:

- 네 변경으로 인해 쓰이지 않게 된 import/변수/함수를 제거하라.
- 요청받지 않은 한, 기존부터 있던 죽은 코드는 제거하지 마라.

판별 기준: 변경된 모든 줄은 사용자의 요청으로 직접 거슬러 올라갈 수 있어야 한다.

## 4. 목표 주도 실행

**성공 기준을 정의하라. 검증될 때까지 반복하라.**

작업을 검증 가능한 목표로 변환하라:

- "검증 추가" → "잘못된 입력에 대한 테스트를 작성한 뒤, 통과시켜라"
- "버그 수정" → "버그를 재현하는 테스트를 작성한 뒤, 통과시켜라"
- "X 리팩터링" → "리팩터링 전후로 테스트가 통과하는지 보장하라"

여러 단계로 이뤄진 작업에는 간략한 계획을 밝혀라:

```
1. [단계] → 검증: [확인]
2. [단계] → 검증: [확인]
3. [단계] → 검증: [확인]
```

강한 성공 기준은 독립적으로 반복할 수 있게 해준다. 약한 기준("그냥 동작하게 해")은 끊임없는 확인을 요구한다.

## 5. 커뮤니케이션 & 에스컬레이션

**사용자 신호를 정확히 해석하라. 불필요하게 되묻지 마라.**

- 오타는 맥락으로 해석하고 되묻지 않는다.
- 사소한 분기(파일명·포맷 등)는 기본값으로 진행하고 1줄 고지한다.
- 같은 지적을 두 번 받으면 즉시 규칙으로 정착시킨다(`.claude/rules/`에 적는다). 세 번째는 없다.
- 해석이 여럿이면 모두 제시하라 — 말없이 하나 고르지 마라.

**다음은 자율 판단 금지 → 진행 전 에스컬레이션:**

- 아키텍처 변경 · 반복 실패 · 스펙 충돌 · 비가역 작업(덮어쓰기·삭제·퍼블리시).
- 정본 소스가 불명확하거나 요구 범위가 서로 충돌할 때.
- 작업 결과가 기존 산출물을 퇴행시킬 것으로 예상될 때.
- 입력이 비어 있거나 대상이 실재하지 않을 때 → 멈추고 먼저 보고(빈 데이터 분석한 척 금지).

**에스컬레이션 포맷:**

```
[ESCALATION]
- 상황: / 막힌 지점: / 시도한 것: / 필요한 결정:
```
