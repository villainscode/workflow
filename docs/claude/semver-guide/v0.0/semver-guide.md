# SemVer 버전 관리 가이드

기준 문서: [Semantic Versioning 2.0.0](https://semver.org/lang/ko/)

## 1. 판단 순서

버전은 `MAJOR.MINOR.PATCH` 형식이다. 위에서부터 차례로 보고 처음 해당하는 자리를 올린다.

- **MAJOR**: 기존 사용자의 코드나 연동이 수정 없이는 동작하지 않을 때. MINOR와 PATCH는 0으로.
- **MINOR**: 기존 동작은 그대로 두고 기능을 추가할 때. PATCH는 0으로.
- **PATCH**: 동작 사양은 바꾸지 않고 버그만 고칠 때.

## 2. 단위별 예시

### MAJOR — 호환이 깨지는 변경

| 구분 | 버전 | 내용 |
|---|---|---|
| ✅ Best | `1.4.2 → 2.0.0` | 응답 필드 `userName`을 `name`으로 변경하고 마이그레이션 문서를 같이 배포. |
| ✅ Best | `1.9.0 → 2.0.0` | 1.x 동안 Deprecated로 예고한 API를 삭제. |
| ❌ Worst | `1.4.2 → 1.5.0` | 필수 파라미터를 추가해 기존 호출이 실패. `^1.4.2`로 의존하던 프로젝트가 자동 업데이트 후 장애. |
| ❌ Worst | `1.4.2 → 2.0.0` | 코드 변경 없이 연도나 홍보 일정에 맞춰 올림. |

### MINOR — 호환되는 기능 추가

| 구분 | 버전 | 내용 |
|---|---|---|
| ✅ Best | `2.0.3 → 2.1.0` | 검색 API에 `sort` 옵션 추가. 옵션을 안 쓰면 이전과 같은 결과. |
| ❌ Worst | `2.1.3 → 2.2.3` | MINOR를 올리면서 PATCH를 0으로 되돌리지 않음. |
| ❌ Worst | `2.1.0 → 2.1.1` | 버그 수정 릴리스에 신규 기능을 함께 넣음. 패치만 받으려던 사용자에게 예상하지 못한 변화가 생긴다. |

### PATCH — 호환되는 버그 수정

| 구분 | 버전 | 내용 |
|---|---|---|
| ✅ Best | `2.1.0 → 2.1.1` | 빈 문자열 입력 시 500 오류가 나던 문제 수정. |
| ✅ Best | `2.1.9 → 2.1.10` | 두 자리를 넘어도 그대로 증가. |
| ❌ Worst | `2.1.1 → 2.1.2` | 버그 수정이라며 타임아웃 기본값을 30초에서 10초로 변경. 동작이 바뀌면 MINOR 이상이다. |
| ❌ Worst | `2.1.1` | 이미 배포한 2.1.1을 같은 번호로 다시 올림. |
| ❌ Worst | `2.01.03` | 앞자리에 0을 붙임. 명세 2항 위반. |

## 3. 공통 규칙

1. 각 자리는 음이 아닌 정수이고 앞자리 0을 붙이지 않는다.
2. 상위 번호를 올리면 하위 번호는 0으로 되돌린다.
3. 배포한 버전의 내용은 바꾸지 않는다. 수정은 새 번호로 낸다.
4. `0.y.z`는 초기 개발 단계다. 공개 API가 확정되면 `1.0.0`.
5. 사전 배포판 순서: `1.0.0-alpha.1` < `1.0.0-rc.1` < `1.0.0`
6. 빌드 정보는 `+` 뒤에 붙인다(`1.0.0+20261016`). 버전 비교에는 쓰이지 않는다.
7. Git 태그는 `v1.2.3`. `v.1.2.3`은 쓰지 않는다.
8. 번호를 올릴 때마다 CHANGELOG에 변경 내용을 적는다.
