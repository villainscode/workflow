SemVer 버전 관리 가이드

기준 문서: Semantic Versioning 2.0.0 (semver.org/lang/ko)

1판단 순서

MAJOR.MINOR.PATCH
MAJOR대규모 기능 변경/정식버전의 소프트웨어 출시/하위버전 호환 보장 안되는 주 업데이트
MINOR새로운 기능을 추가할 때, 하위 호환 보장
PATCH기존 버전 호환되며 버그 패치, 소규모 수정(기능 동작이 바뀌면 Minor)

2단위별 예시

구분Best 예시Worst 예시
MAJOR (주(主) 버전)호환이 깨지는 변경

1.4.2 → 2.0.0응답 필드 userName을 name으로 변경하고 마이그레이션 문서를 같이 배포.

1.9.0 → 2.0.0 1.x 동안 Deprecated로 예고한 API를 삭제.

1.4.2 → 2.0.0코드 변경 없이 연도나 홍보 일정에 맞춰 올림.
MINOR (부(副) 버전) 호환되는 기능 추가

2.0.3 → 2.1.0검색 API에 sort 옵션 추가. 옵션을 안 쓰면 이전과 같은 결과.

2.1.3 → 2.2.3MINOR를 올리면서 PATCH를 0으로 되돌리지 않음.

2.1.0 → 2.1.1버그 수정 릴리스에 신규 기능을 함께 넣음. 패치만 받으려던 사용자에게 예상하지 못한 변화가 생긴다.
PATCH (수(修) 버전)호환되는 버그 수정

2.1.0 → 2.1.1빈 문자열 입력 시 500 오류가 나던 문제 수정.

2.1.9 → 2.1.10두 자리를 넘어도 그대로 증가.

2.1.1 → 2.1.2버그 수정이라며 타임아웃 기본값을 30초에서 10초로 변경. 동작이 바뀌면 MINOR 이상이다.

2.1.1이미 배포한 2.1.1을 같은 번호로 다시 올림.

2.01.03앞자리에 0을 붙임. 명세 2항 위반.

3공통 규칙

  1. 각 자리는 음이 아닌 정수이고 앞자리 0을 붙이지 않는다.
  2. 상위 번호를 올리면 하위 번호는 0으로 되돌린다.
  3. 배포한 버전의 내용은 바꾸지 않는다. 수정은 새 번호로 낸다.
  4. 0.y.z는 초기 개발 단계다. 공개 API가 확정되면 1.0.0.
  5. 사전 배포판 순서: 1.0.0-alpha.1 < 1.0.0-rc.1 < 1.0.0
  6. 빌드 정보는 + 뒤에 붙인다(1.0.0+20261016). 버전 비교에는 쓰이지 않는다.
  7. Git 태그는 v1.2.3. v.1.2.3은 쓰지 않는다.
  8. 번호를 올릴 때마다 CHANGELOG에 변경 내용을 적는다.
