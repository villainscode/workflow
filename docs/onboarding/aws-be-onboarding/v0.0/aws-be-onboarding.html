03

staging 도메인 연결

인증서 검증 → CloudFront에 도메인 연결 → DNS Alias 순서로 진행합니다.

ACM 인증서의 DNS 검증 완료하기

ACM 콘솔의 리전을 미국 동부(버지니아 북부), us-east-1로 선택합니다. staging 인증서를 열고 DNS 검증 CNAME을 확인하세요. Route 53의 habilis-console.com 영역에 동일한 이름과 값을 등록합니다. ACM의 “Route 53에서 레코드 생성” 기능을 사용해도 됩니다.

CloudFront에 인증서와 도메인 설정하기

인증서 상태가 Issued가 되면 staging 배포의 설정을 편집합니다. 대체 도메인 이름에 staging.habilis-console.com을 추가하고, 발급된 staging 인증서를 선택합니다. TLS 정책은 TLSv1.2_2021 이상을 사용합니다.

Route 53에서 A / AAAA Alias 연결하기

staging 배포의 업데이트가 끝난 뒤, staging.habilis-console.com의 A 및 AAAA 레코드를 생성합니다. Alias 대상으로 staging CloudFront 배포를 선택합니다. 대상 도메인은 d2l8g9r5gc0jlt.cloudfront.net입니다.

인증서와 DNS 상태 확인하기

인증서가 발급되었고 DNS가 새 배포를 가리키는지 확인합니다. 파일을 아직 올리지 않은 버킷에서는 HTTP 403이 나타날 수 있습니다. 인증서 검증 CNAME은 자동 갱신에 쓰이므로 유지합니다.

현재 인증서 검증 CNAME 보기 · 두 환경
aws acm describe-certificate \
  --certificate-arn arn:aws:acm:us-east-1:668826142093:certificate/96892f50-401f-46b6-b24e-47a8055eb1f2 \
  --region us-east-1 --profile namhee \
  --query 'Certificate.{Status:Status,Validation:DomainValidationOptions}'

aws cloudfront get-distribution --id EI65XK2M8PUZL \
  --profile namhee --query 'Distribution.Status'

dig staging.habilis-console.com
S3는 비공개이며 CloudFront OAC를 통해 파일을 제공합니다. S3 웹사이트 엔드포인트 대신 S3 REST origin을 유지하세요. 도메인 확인을 위해 버킷을 공개할 필요는 없습니다.

07
staging에 어떤 서비스를 만들까요?

RDSPostgreSQL Multi-AZ DB instance · primary + 다른 AZ standby예비 DB는 장애 전환용이며 읽기 요청을 나누어 처리하지 않습니다. 장애 전환 후 앱이 다시 연결되는지 확인합니다. 읽기 성능 확장은 별도 복제본이나 클러스터로 검토합니다.


Redis / Valkeyprimary + 다른 AZ replica · Multi-AZ + automatic 장애 전환복제가 끝나기 전에 장애가 나면 일부 데이터가 유실될 수 있습니다. 중요한 원본 데이터는 DB에 보관하고, 캐시 장애 시 요청 횟수 제한과 세션을 어떻게 처리할지 정합니다.


외부 통신Zonal NAT Gateway를 AZ별 1개, 앱은 같은 AZ NAT 사용NAT나 WireGuard 게이트웨이 한 대의 장애로 모든 앱의 외부 통신이 끊기지 않도록 합니다.


AWS 내부 접근S3 gateway 엔드포인트, 필요 시 ECR·SSM·Logs·Secrets Manager interface 엔드포인트엔드포인트의 DNS·보안 그룹·AZ 배치를 확인합니다. 외부 API나 패키지 저장소에 접속하는 경로와 AWS 서비스에 접속하는 경로를 구분합니다.

staging과 운영 환경에서 같게 유지할 것


staging과 PROD는 ALB·API EC2·RDS PostgreSQL·ElastiCache Valkey라는 서비스 구성을 맞춥니다. Terraform 서비스 모듈·엔진 메이저 버전·파라미터·인증/TLS·마이그레이션 절차를 가능한 한 공유하고 Terraform 상태 파일(state), 비밀번호·키 같은 시크릿, 실제 데이터는 환경별로 따로 관리합니다. staging은 API 1대·RDS Single-AZ·캐시 1노드로 운영합니다. staging API는 기존 공용 서브넷을 재사용하므로 PROD 목표의 비공개 앱 서브넷·ASG와도 차이가 있습니다. 환경 분리·동일 이미지 배포·DB 마이그레이션·롤백 절차를 먼저 맞춥니다. 운영 환경을 이전하기 전에는 staging에서도 API 서버와 DB·캐시를 이중화해, 장애가 났을 때 전환과 재연결이 되는지 시험합니다. 예비 DB, 캐시 복제본, NAT, VPC 엔드포인트를 늘리면 상시 비용도 늘어납니다. 필요한 장애 대응 수준을 정한 뒤 추가합니다.


운영 환경의 네트워크 이전 순서 (cch 담당)


  1. 확정된 CIDR을 IP 관리대장에 반영하고 사무실/VPN 라우팅·SG·운영 경로를 검토합니다.
  2. 새 VPC·두 AZ 인프라를 별도 state로 구축하고, 기존 prod는 유지한 채 새 앱을 검증합니다.
  3. DB 이전은 허용 중단 시간에 따라 스냅샷 복원 또는 변경 데이터 복제 방식으로 별도 설계합니다. Redis의 세션·rate-limit 데이터 보존/초기화 방침도 정합니다.
  4. 최종 데이터 동기화·쓰기 전환·API DNS 전환 순서를 정하고, 배포 전 합의한 검증 기준을 확인합니다.
  5. 새 DB에 쓰기가 시작된 뒤에는 DNS만 원복하면 데이터가 갈라질 수 있습니다. 데이터 역동기화 또는 쓰기 중단을 포함한 롤백 조건과 종료 시점을 먼저 정합니다.
  6. 관찰 기간과 복구 검증을 마친 뒤 기존 자원을 정리합니다. 이 작업은 남희님의 staging 완료 조건에 포함하지 않습니다.

  5. API 서비스만 포함한 staging Compose를 작성합니다. 로컬 개발용 루트 compose.yaml의 PostgreSQL·Valkey 서비스를 배포하지 않습니다. RDS·ElastiCache 엔드포인트와 staging 시크릿을 API에 전달합니다.

  7. RDS 자동 백업은 7일간 보관합니다. 삭제 보호를 켜고 DB 삭제 시 마지막 스냅샷을 남기도록 설정합니다. 복구 연습에서는 백업을 별도 DB 인스턴스로 복원해 확인합니다. ElastiCache는 현재 rate-limit 카운터 용도에 맞춰 데이터 유실 시 동작과 재시작 후 복구 방침을 기록합니다.

staging은 사내망과 회사 VPN에서만 접근합니다


ALB의 80·443 포트를 모든 인터넷 주소(0.0.0.0/0)에 열지 않습니다. 사내망과 회사 VPN을 통한 접속만 허용하고, 회사 밖에서 VPN을 끈 상태에서는 접근할 수 없어야 합니다.


공개 ALB에 접속 출처를 제한합니다. 운영 환경과 마찬가지로 인터넷 요청을 받는 ALB를 사용하되, staging의 80·443 포트는 사무실과 회사 VPN의 고정 공인 출구 IP만 허용합니다. HTTPS 인증서와 DNS 연결 방식은 운영 환경과 같게 유지합니다.


Terraform에서는 허용 주소 목록을 alb_allowed_ipv4_cidrs 변수로 분리합니다. staging에는 확인된 사무실·VPN 공인 IP를 등록하고, 일반 사용자에게 공개하는 운영 환경에는 0.0.0.0/0을 설정합니다. 공인 IP 한 개는 /32로 등록하며, 회사가 사용하는 출구가 여러 개면 각각 추가합니다. 두 환경의 변수 파일은 별도로 관리합니다.


staging 변수에는 전체 인터넷 허용 값을 기본값으로 두지 않습니다. 허용 목록이 비어 있거나 0.0.0.0/0처럼 전체 인터넷을 포함하면 배포 전에 검증에서 실패하도록 작성합니다. 실제 공인 IP는 네트워크 담당자에게 확인해 등록하고, 임시로 개인 집 IP나 넓은 주소 범위를 추가하지 않습니다.


공개 ALB에 사내 사설 IP 대역만 넣어서는 접속할 수 없습니다. 또한 VPN을 켜도 인터넷 트래픽은 집 회선으로 나갈 수 있으므로, VPN을 통한 API 접속이 실제로 어떤 출구를 사용하는지 확인합니다. 라우팅의 기본 경로나 서버의 아웃바운드에 쓰는 0.0.0.0/0은 외부 접속을 허용하는 인바운드 규칙과 다릅니다.


브라우저는 CloudFront에서 화면을 받은 뒤 API에 직접 요청합니다. API 접근을 위해 CloudFront 전체 IP를 허용할 필요는 없습니다. 프런트엔드 화면 자체도 사내 전용으로 제한하려면 staging CloudFront에 별도의 접근 제어를 적용해야 합니다. API 보안 그룹만으로 화면까지 비공개가 되지는 않습니다.

서버 / 아웃바운드초기 staging: 0.0.0.0/0처음에는 서버가 외부로 나가는 통신을 모두 허용합니다. 패키지 설치, 이미지 다운로드, SSM, AWS API에 필요한 연결을 조사한 뒤 목적지와 포트를 좁히는 개선안을 정리합니다.




서버 인바운드에 SSH 22·PostgreSQL 5432·Valkey 6379 규칙을 추가하지 않습니다. 서버 접속은 SSM을 사용하고 API → RDS·ElastiCache는 VPC 사설 통신을 사용합니다. 보안 그룹을 여러 개 연결하면 각 그룹의 허용 규칙이 모두 적용됩니다. 서버에는 API 전용 보안 그룹만 연결하세요.


  1. 설계: 사내망·회사 VPN → ALB → API, ALB → 상태 확인, API → DB/Valkey, 서버 → AWS 서비스 경로를 그립니다. 각 경로의 출발지·목적지·포트와 적용되는 SG를 설명합니다.
  2. 구현: 위 규칙을 Terraform으로 작성하고 plan에서 새 SG와 규칙만 의도대로 추가되는지 확인합니다. ALB의 기본 전체 아웃바운드 규칙이 남지 않도록 관리합니다. SG 간 참조 규칙을 별도 리소스로 작성하면 상호 참조로 인한 의존성 순환을 피할 수 있습니다.
  3. 정상 연결 확인: 배포 후 ALB를 통한 HTTPS 요청과 대상 그룹의 정상 상태(healthy)를 확인합니다. SSM 접속, ECR 이미지 다운로드, DB 읽기·쓰기, 캐시를 이용한 요청 횟수 제한도 확인합니다.
  4. 접근 차단 확인: 사내망·회사 VPN에서는 API HTTPS 요청이 성공하고, 휴대폰 테더링 등 외부망에서 VPN을 끄면 접근이 차단되는지 확인합니다. 외부 클라이언트에서 EC2 공인 IP의 8080·9090·22·5432·6379에 직접 연결되지 않는지 확인합니다. 타임아웃만으로 SG 차단을 단정하지 말고, 8080·9090은 서버 내부 응답 및 ALB 경유 성공과 함께 비교합니다. DB·캐시 SG에는 서버 SG만 출발지로 지정됐는지 확인합니다. 서버 내부에서 관리형 엔드포인트 연결이 성공하는지 확인하고, 서버 SG가 없는 별도 테스트 ENI에서의 경로는 Reachability Analyzer 등으로 차단을 확인합니다.
  5. 결과 정리: Terraform 코드, 규칙별 허용 이유, 테스트 출발지·목적지·결과를 남깁니다. 보안 그룹과 서브넷 단위 접근 제어인 NACL의 차이를 설명해 봅니다. 연결 상태를 기억하는 stateful 방식이 무엇인지, IP 범위를 허용할 때와 다른 보안 그룹을 지정할 때 무엇이 다른지도 정리합니다. CORS만으로 서버 접근을 막을 수 없는 이유도 설명해 보세요.

RDS·ElastiCache 생성 후 AWS가 제공하는 DNS 엔드포인트를 API 설정에 사용합니다. 콘솔 또는 Terraform output에서 엔드포인트를 확인하고, IP를 직접 입력하거나 DNS 조회 결과를 고정해서 저장하지 않습니다. 장애 복구·서버 교체로 IP가 바뀔 수 있으므로 앱은 이 주소를 사용해 다시 연결하도록 구성합니다.


서비스사용할 주소API 환경변수
RDS PostgreSQLstaging DB 인스턴스의 접속 주소(Endpoint) · TCP 5432DB_HOST=<RDS endpoint>
ElastiCache Valkeystaging 캐시 복제 그룹의 주 노드 주소(Primary endpoint) · TCP 6379REDIS_HOST=<Primary endpoint>
REDIS_PORT=6379


현재 캐시는 데이터를 여러 샤드로 나누지 않는 구성(cluster mode disabled)입니다. 읽기와 쓰기 모두 주 노드의 주소(Primary endpoint)를 사용합니다. 호스트 이름에는 https://나 포트를 붙이지 않습니다. TLS·인증은 별도 클라이언트 설정으로 적용합니다.


도메인 형태의 주소가 인터넷 공개를 의미하지는 않습니다. RDS의 퍼블릭 액세스는 끄고, DB와 캐시는 별도 데이터 서브넷에 배치합니다. 각 서비스의 보안 그룹은 API 서버의 보안 그룹에서 오는 5432·6379 연결만 허용합니다. API 서버에서 DNS 해석과 인증 정보를 사용한 DB·캐시 연결을 확인합니다.


운영 Terraform은 terraform/environments/prod/에 있습니다. 기존 운영 state 키는 유지하며, staging 구축은 terraform/environments/staging/에서 별도로 작성합니다. 기존 v*·infra-v* 배포는 운영 전용입니다.

DB_PASSWORD·JWT_SECRET는 staging 시크릿에서 읽어 umask 077로 만든 .env에 저장하고 chmod 600을 적용합니다. 관리형 서비스 엔드포인트와 인증/TLS 설정이 애플리케이션까지 전달되는지 확인하세요. 아직 API 이미지가 없다면 DB와 캐시를 먼저 준비한 뒤, 첫 앱 배포에서 API를 시작합니다.
Redis에서 TLS나 인증을 켰다면 REDIS_SSL_ENABLED·REDIS_USERNAME·REDIS_PASSWORD도 전달합니다. Swagger를 열려면 SWAGGER_ALLOWED_IPS에 사무실·VPN 공인 IP를 지정합니다. staging에서는 SENTRY_DSN을 지정해야 오류가 수집되며, 다운로드 기능을 사용하려면 DELIVERY_BASE_URL도 정해야 합니다. 운영 서비스 주소와 자격 증명을 그대로 복사하지 않습니다.

API 도메인에 HTTPS 연결하기
브라우저의 HTTPS 요청은 ALB가 받은 뒤 API 서버로 전달합니다.


  1. 앞에서 정한 AZ A/C의 퍼블릭 서브넷에 인터넷 요청을 받는(internet-facing) ALB habilis-api-staging-alb를 생성합니다. 각 서브넷의 전용 라우팅 테이블은 기존 IGW로 연결합니다. ALB 보안 그룹의 80·443 포트에는 사무실·회사 VPN 공인 IP만 허용합니다.
  2. 아래 서울 리전 ACM 인증서의 DNS 검증 CNAME을 등록합니다. 인증서 상태가 ISSUED인지 확인한 후 HTTPS 리스너에 연결합니다. DNS 검증 레코드는 갱신을 위해 유지합니다.
  3. ALB의 443 포트에 HTTPS 리스너를 만들고, API 서버의 8080 포트로 전달하는 대상 그룹(Target Group)을 연결합니다. 대상 그룹에는 새 API EC2를 등록합니다. AZ 간 요청 분산(cross-zone)은 켜 두고, 80 포트의 HTTP 요청은 HTTPS로 이동시킵니다.
  4. 대상 그룹은 HTTP 9090 포트의 /actuator/health/readiness에 요청해 앱이 준비됐는지 확인합니다. EC2 SG에서 ALB SG의 8080·9090만 허용합니다. 외부에서 접근하는 ALB 리스너에는 9090 포트를 연결하지 않습니다.
  5. api-staging.habilis-console.com의 A Alias를 ALB로 연결합니다. EC2 공인 IP나 EIP를 DNS에 넣지 않습니다. IPv4 구성이므로 AAAA는 만들지 않습니다.
  6. 대상 그룹이 healthy 상태인지 확인한 뒤 HTTPS 인증서와 사내망·회사 VPN에서의 /health, 실제 브라우저 API 요청을 확인합니다. API 서버가 한 대이므로 재시작 중에는 502 또는 503 오류가 발생할 수 있습니다.

  1. 인프라 배포: staging 전용 Terraform 디렉터리에서 초기화(init), 문법 검사(validate), 변경 계획 확인(plan), 적용(apply)을 수행하는 수동 워크플로를 작성합니다. 운영 환경과 상태 파일을 분리하고, 이번에 만들 API 자원만 변경되는지 확인합니다.
  2. 앱 배포: 테스트가 통과하면 Jib으로 ARM64 이미지를 만들고, sha-<commit> 태그를 붙여 ECR에 올립니다. SSM의 AWS-RunShellScript로 API 서버의 deploy.sh를 실행합니다. SSM 명령이 성공적으로 끝났는지와 서버 내부의 앱 상태를 확인합니다. ALB를 통한 HTTPS 검사는 사내망·VPN에 연결된 실행 환경에서 수행합니다. 일반 GitHub 호스팅 러너는 허용된 접속 출처가 아니므로, 검사를 통과시키기 위해 ALB를 전체 인터넷에 열지 않습니다.
  3. 서버 스크립트: 이미지 태그가 정해진 형식인지 검사하고, flock으로 배포 스크립트가 동시에 실행되지 않게 합니다. EC2 역할로 ECR에 로그인하고 시크릿을 읽습니다. 새 이미지를 내려받아 docker compose up -d --no-deps api로 실행한 뒤, 서버 내부에서 앱이 요청을 받을 준비가 됐는지 확인합니다. RDS·ElastiCache 자원은 앱 배포에서 변경하지 않습니다.
  4. 배포 기록: 교체하기 전에 현재 실행 중인 이미지 태그를 저장합니다. 배포가 성공하면 /habilis-api/staging/image-tag 값을 갱신하고, 배포한 커밋 SHA와 SSM 명령 ID를 기록합니다. 기록만 바뀐 것으로 배포를 완료하지 말고, 새 이미지가 실제로 실행 중인지 확인합니다.
  5. 실패하면 이전 버전으로 복구: 앱이 요청을 처리할 준비가 되지 않았다면 직전 이미지로 API 컨테이너를 다시 실행하고 상태를 확인합니다. 서버가 한 대라 복구 중 잠깐 중단될 수 있습니다. 앱을 되돌려도 DB 구조는 자동으로 돌아가지 않으므로, DB 변경은 이전 앱에서도 동작하도록 작성합니다.
  6. 동시 배포: AWS 자원을 변경하는 작업은 concurrency 그룹을 api-staging-mutate로 지정하고 cancel-in-progress: false를 설정해 한 번에 하나씩 실행합니다. Actions가 끝나도 SSM 명령은 계속 실행될 수 있습니다. 명령의 제한 시간을 설정하고 서버에서도 flock으로 중복 실행을 막습니다.
