01

계정과 로컬 프로필 준비

일반 조회는 default, 환경 설정은 명시적으로 --profile namhee.

개인 계정: namhee@tommoro.ai · AWS 계정 ID: 668826142093

AWS 콘솔 로그인 ↗내 보안 자격 증명 ↗
  1. 별도로 전달받은 임시 비밀번호로 로그인하고, 첫 로그인에서 비밀번호를 변경합니다.
  2. 내 보안 자격 증명에서 MFA를 등록합니다. 가상 MFA 장치 이름은 namhee@tommoro.ai로 지정합니다.
  3. AWS CLI v2.32 이상에서 아래 명령으로 개인 프로필을 연결합니다.
aws configure set region ap-northeast-2 --profile namhee
aws login --profile namhee
aws sts get-caller-identity --profile namhee

마지막 명령의 ARN이 arn:aws:iam::668826142093:user/namhee@tommoro.ai인지 확인합니다. 세션 만료 시 같은 aws login --profile namhee 명령을 다시 실행합니다.

에이전트용 default 프로필도 구성하기

별도로 전달받은 namhee-readonly@tommoro.ai의 액세스 키를 default에 등록합니다. 이 계정은 AWS 전체 조회용 ReadOnlyAccess를 갖습니다. 작업 중인 로컬에 이미 다른 default 계정이 있다면 먼저 계정 소유자와 확인하세요.

aws configure --profile default
aws sts get-caller-identity

# 설정 작업에만 개인 프로필을 지정
aws route53 list-hosted-zones --profile namhee

AWS_PROFILE=namhee를 전역으로 설정하지 않습니다. 에이전트의 일반 조회는 default를 사용하고, 요청한 설정 작업에만 개인 프로필을 지정합니다.

참고: 현재 cch 로컬에서 사용하는 방식

현재 cch 로컬의 default는 에이전트 조회용 cch-tommoro-claude 계정입니다. 별도 권한이 필요한 작업에만 --profile cch를 명시합니다.

# 일반 조회: default 사용
aws sts get-caller-identity
aws route53 list-hosted-zones

# 권한이 필요한 작업: 명령마다 cch 명시
aws sts get-caller-identity --profile cch

# cch 세션이 만료되었을 때
aws login --profile cch

AWS_PROFILE=cch를 전역으로 설정하지 않습니다. 남희님은 같은 사용 방식으로 본인의 --profile namhee를 사용합니다. cch 계정 자격 증명을 공유할 필요는 없습니다.

03

staging 도메인 연결

인증서 검증 → CloudFront에 도메인 연결 → DNS Alias 순서로 진행합니다.

ACM 인증서의 DNS 검증 완료하기

ACM 콘솔의 리전을 미국 동부(버지니아 북부), us-east-1로 선택합니다. staging 인증서를 열고 DNS 검증 CNAME을 확인하세요. Route 53의 habilis-console.com 영역에 동일한 이름과 값을 등록합니다. ACM의 “Route 53에서 레코드 생성” 기능을 사용해도 됩니다.

CloudFront에 인증서와 도메인 설정하기

인증서 상태가 Issued가 되면 staging 배포의 설정을 편집합니다. 대체 도메인 이름에 staging.habilis-console.com을 추가하고, 발급된 staging 인증서를 선택합니다. TLS 정책은 TLSv1.2_2021 이상을 사용합니다.

Route 53에서 A / AAAA Alias 연결하기

staging 배포의 업데이트가 끝난 뒤, staging.habilis-console.com의 A 및 AAAA 레코드를 생성합니다. Alias 대상으로 staging CloudFront 배포를 선택합니다. 대상 도메인은 d2l8g9r5gc0jlt.cloudfront.net입니다.

인증서와 DNS 상태 확인하기

인증서가 발급되었고 DNS가 새 배포를 가리키는지 확인합니다. 현재 버킷은 비어 있으므로 첫 배포 전의 HTTP 403은 정상입니다. 인증서 검증 CNAME은 자동 갱신에 쓰이므로 유지합니다.

현재 인증서 검증 CNAME 보기 · 두 환경
aws acm describe-certificate \
  --certificate-arn arn:aws:acm:us-east-1:668826142093:certificate/96892f50-401f-46b6-b24e-47a8055eb1f2 \
  --region us-east-1 --profile namhee \
  --query 'Certificate.{Status:Status,Validation:DomainValidationOptions}'

aws cloudfront get-distribution --id EI65XK2M8PUZL \
  --profile namhee --query 'Distribution.Status'

dig staging.habilis-console.com
준비된 S3는 비공개이며 CloudFront OAC를 통해 파일을 제공합니다. S3 웹사이트 엔드포인트 대신 S3 REST origin을 유지하세요. 도메인 확인을 위해 버킷을 공개할 필요는 없습니다.
04

GitHub 환경 설정

환경 이름과 브랜치는 AWS 역할의 신뢰 조건과 정확히 맞아야 합니다.

Tommoro-AI / habilis_console_web ↗의 Settings → Environments에 staging과 prod를 만듭니다.

환경허용 브랜치배포 도메인
stagingdevelopstaging.habilis-console.com
prodmainweb.habilis-console.com
저장소 관리자와 확인할 항목
남희님의 저장소 Write 권한, 환경 생성·Variables/Secrets 설정 권한, prod 배포 검토자와 브랜치 보호 규칙을 확인합니다. AWS 권한만으로 GitHub 권한이 생기지는 않습니다. main이 없다면 팀의 브랜치 운영 방식에 맞춰 생성합니다.

각 GitHub Environment에 넣을 Variables

선택한 환경의 값을 확인해 등록하세요. 아래 값은 Secret이 아닌 Variable로 등록합니다.


        
HDS 비공개 서브모듈: 기존 CI는 HDS_REPO_TOKEN Secret을 참조합니다. 토큰이 준비되어 있는지 관리자와 확인하고, 콘솔 저장소 및 habilis-design-system의 필요한 읽기 권한만 부여합니다. 토큰 값은 코드나 문서에 적지 않습니다.

        
AWS가 실제로 검사하는 OIDC 조건
두 역할은 저장소 ID 1418533009, 조직 ID 179105444, Audience sts.amazonaws.com을 검사합니다. 환경과 브랜치도 함께 확인하므로 다른 브랜치에서 prod 역할을 사용할 수 없습니다.
staging: environment:staging + refs/heads/develop
prod: environment:prod + refs/heads/main
신뢰 정책은 이 저장소의 ID가 포함된 immutable subject 형식을 사용합니다. 역할을 새로 만들거나 개인 AWS 키를 GitHub Secret으로 등록할 필요는 없습니다.

        
      

    


    

      
05
자동 배포 워크플로 직접 구현
이번 온보딩의 핵심 과제입니다. 배포 워크플로는 남희님이 작성합니다.

      

        
.github/workflows/deploy-static.yml을 새로 작성하고 PR을 올려 주세요. 기존 console_old 배포 워크플로에서 전체 흐름을 참고하되, 새 저장소의 Vite·pnpm 구조와 두 환경에 맞춰 설계합니다.

        
빌드 산출물은 apps/web/dist입니다.
기존 Next.js의 out/·_next/static 대신 Vite의 dist/·assets/를 사용합니다.

        
# Node 버전은 저장소의 .nvmrc 기준 (현재 24)
git submodule update --init --recursive
corepack enable pnpm
pnpm hds:build
pnpm install --frozen-lockfile
pnpm format:check
pnpm lint
pnpm typecheck
pnpm test
pnpm build

# 실제 빌드 결과 확인
ls apps/web/dist

        
워크플로에 담아야 할 요구사항

        
    
          
  • 트리거와 환경 선택
    develop → staging, main → prod. 수동 실행도 해당 브랜치와 환경 조합을 유지합니다. job에 GitHub environment를 지정합니다.
    • 
          
  • 검증이 성공한 산출물만 배포
    비공개 HDS 서브모듈을 포함해 checkout하고, HDS 빌드·앱 의존성 설치·코드 검사·테스트·앱 빌드를 수행합니다. 배포 전에 index.html과 assets 디렉터리가 있는지 확인합니다.
    • 
          
  • OIDC로 AWS 인증
    job의 id-token: write와 contents: read를 설정합니다. aws-actions/configure-aws-credentials에서 환경별 역할 ARN과 서울 리전을 사용합니다.
    • 
          
  • 파일 업로드 순서와 캐시 설계
    해시가 포함된 assets/를 먼저 올리고 장기 immutable 캐시를 적용합니다. HTML·일반 파일은 재검증하도록 설정합니다. 열린 이전 탭이 쓰는 assets를 즉시 삭제하지 않도록 sync의 삭제·제외 범위를 정합니다.
    • 
          
  • 해당 환경의 CloudFront 캐시 무효화
    업로드 성공 후 배포 ID로 invalidation을 생성하고 완료를 확인합니다. staging 역할은 prod 리소스에 접근할 수 없습니다.
    • 
          
  • 동시 배포와 실패 처리
    환경별 concurrency로 업로드가 섞이지 않게 합니다. 검증 실패·업로드 실패는 실패로 종료하고, 사용한 커밋과 Actions 실행 결과를 남깁니다.
    • 
        

        
처음 구현할 때 자주 만나는 문제
AssumeRoleWithWebIdentity가 거부됨
선택한 environment, 브랜치, 역할 ARN을 함께 확인합니다. env 이름은 prod이며 production이 아닙니다.
HDS checkout 또는 import 실패
Secret의 저장소 접근 범위와 submodule checkout 여부를 확인합니다. HDS는 앱 의존성 설치 전에 빌드해야 합니다.
개인 계정으로 S3 업로드가 거부됨
예상된 권한 동작입니다. 업로드는 워크플로의 배포 역할로 수행합니다.
루트는 열리지만 /login 새로고침이 실패함
준비된 SPA 함수가 기본 cache behavior의 viewer-request에 연결되어 있는지 확인합니다. /assets/*는 파일 그대로 제공해야 합니다.
설정은 맞지만 API 호출이 실패함
staging API 주소와 프런트의 API 설정 방식은 프런트·서버 팀과 정합니다. 이번 기본 구성에는 API origin이 연결되어 있지 않습니다.

        
      

    


    

      
06
prod 배포와 완료 검증
staging에서 확인한 배포 흐름을 prod 환경에 적용합니다.

      

        
  1. staging에서 첫 화면, 정적 파일 로딩, /login·/workspace 직접 접근과 새로고침을 확인합니다.
  2. 03단계와 같은 순서로 web.habilis-console.com의 인증서를 검증하고 prod CloudFront·DNS를 연결합니다.
  3. 검토된 변경을 main에 반영하고 prod 환경의 배포를 실행합니다.
  4. 두 환경의 도메인·배포 ID·커밋을 확인하고, 브라우저 캐시가 남아 있어도 새 버전이 열리는지 확인합니다.
  5. 문제가 생겼을 때 이전 정상 커밋으로 되돌리는 절차를 작성합니다. 예를 들어 revert PR을 반영해 동일한 파이프라인으로 재배포합니다.
