플랫폼팀 개발 환경

제품은 현장 디바이스 위에서 돕니다. habilis_console이 모든 디바이스에 설치되는 런타임이고, 기능은 전부 그 위에 올라가는 확장팩입니다. 클라우드에는 계정 · 배포 · 관측성만 있습니다.

언어는 Rust · Python · Kotlin이 기준 없이 섞여 있습니다. 역사적으로 그렇게 됐고 아직 정리하지 않았습니다.

목차

구조 파이프라인 저장소 사내 네트워크 모니터링 개발 플로우 처음 붙을 때 용어

01

구조

이 그림 하나가 거의 전부입니다. 런처가 런타임이고, 기능은 전부 그 위에 올라가는 확장팩입니다.

런처가 바뀌면 모든 확장팩에 영향이 갑니다. 모든 디바이스에 설치되는 유일한 공통 지점이라서요.

확장팩끼리는 서로를 모릅니다. 각 팩은 자기 Docker 컨테이너 안에서 돌기 때문에, 팩 하나를 고치는 작업은 대체로 그 팩 안에서 끝납니다.

버전이 같이 움직입니다. 런처와 팩들이 전부 v0.9.0-dev.x 대역에 있습니다. 팩 하나만 올리는 게 아니라 조합으로 움직입니다.

영역무엇
콘솔 · 런처Tauri · Rust · Next.jsSSR 미사용
확장팩 실행Docker런처에 내장

백엔드 APIKotlin · Spring인증 · 사용자 · 기능 플래그. 온프레미스를 고려하지 않은 스택 — 변경 검토 중
관측성OTLP · ClickHouse · Grafana · GlitchTipedge에서 모아 backend에서 저장
데이터셋MCAP · LeRobot · NAS · SFTP
인프라현장 온프레미스 · AWS

백엔드 API 스택은 바뀔 수 있습니다. Kotlin · Spring은 클라우드를 전제로 고른 스택이라 온프레미스를 고려하지 않았습니다. 무엇으로 갈지는 아직 정해지지 않았습니다.

Next.js를 SSR 없이 쓰는 건 Tauri 시절 유산입니다. 정적 번들을 로드해야 해서 못 썼고 그 설정이 남았습니다. 데스크톱 앱은 걷어내는 중이고 웹이 default지만, 디바이스에 설치되는 런타임이라는 역할은 남습니다.

02

파이프라인 — 콘솔이 커버하는 범위

제품이 하는 일을 한 줄로 줄이면 로봇에서 데이터를 모아 모델을 만들고 다시 로봇에 태우는 것입니다. 콘솔은 이 네 단계를 한 화면에서 돌리는 걸 목표로 하고 있고, 단계마다 덮인 정도가 다릅니다.

단계확장팩관리 팀
수집dataset_manager콘솔 UI에서 녹화 — 에피소드 단위플랫폼팀
수집 · 자동CONE-DA궤적을 만들어 사람 없이 모읍니다에이전트팀
변환dataset_managerMCAP을 LeRobot 데이터셋으로. NAS · SFTP 전송까지플랫폼팀
학습ai_managerACT · DP · SmolVLA · Pi0.5 · GR00T 등에이전트팀
추론ai_manager체크포인트를 골라 정책 서버로 실행에이전트팀
로봇에 전달rosbridge · console추론 결과를 ROS2로 내려보냅니다플랫폼팀

플랫폼팀이 직접 만드는 건 앞의 두 단계입니다. 학습 · 추론은 ai_manager가 하고, 콘솔은 그걸 설치 · 실행 · 모니터링하는 자리를 내어줍니다.

어디서 막히나

  • 팀마다 따로

    데이터팀과 콘솔이 수집 · 변환을 각자 만들고 있고 결과물 형식이 조금씩 다릅니다. LeRobot 기반 공통 kit와 인터페이스로 묶자는 논의가 개발본부에서 진행 중입니다.

  • 변환에서 깨짐

    observation · action 개수 불일치, 카메라 해상도 validation, ROS 토픽 이름 변경 같은 이유로 변환이 막히는 일이 반복됩니다. 전처리 로직을 dataset_manager에 둘지 ai_manager에 둘지도 아직 정해지지 않았습니다.

  • 체크포인트

    콘솔이 만든 체크포인트는 콘솔에서 바로 고를 수 있지만, 밖에서 학습한 건 지정 경로에 직접 넣어줘야 합니다.

  • 자원

    GPU와 디스크가 수시로 모자랍니다. 수집 중에 디스크가 차서 녹화가 멈춘 적이 있고, 확장팩이 GPU를 요구해서 노트북에서는 테스트가 안 됩니다.

  • 버전 조합

    룸마다 설치된 확장팩 조합이 다르면 UI가 아예 안 뜹니다. dataset_manager가 없는 콘솔에서는 「원본」 · 「데이터셋」 화면을 쓸 수 없습니다.

04

사내 네트워크

IP만 보고도 어느 층 어느 룸의 무슨 장비인지 알 수 있게 대역이 나뉘어 있습니다. 규칙 하나만 외우면 됩니다.

대역어디
10.0.0.0/16사무실 7층
10.1.0.0/16사무실 6층
10.20.0.0/16베트남
10.101.0.0/16클라우드 staging — AWS VPC. 테스트 환경 전체
10.100.0.0/16클라우드 prodstaging 안정화 후 도입 검토 — 아직 미구축

호스트 번호 규칙 — 10.<층>.<룸>.10 = PC, .11 = 로봇

10.0.3.11 은 7층 room-3 의 로봇, 10.1.11.10 은 6층 room-11 의 워크스테이션입니다. 클라우드 staging도 같은 규칙을 그대로 씁니다.

VPN

사무실 wifi에서는 VPN 없이 접속됩니다. 외부에서 사내망에 들어올 때만 필요합니다.

WireGuard를 쓰고, .conf 파일을 사람·기기 단위로 발급합니다. 클라이언트를 설치한 뒤 받은 conf를 불러오면 됩니다. 발급은 플랫폼팀에 요청하세요.

외부 → VPN → gw → AWS VPC 순으로 들어갑니다. admin.habilis-console.com 같은 내부 서비스는 VPN이나 사내망에서만 열립니다.

고객 현장은 사내망과 다릅니다

여기가 개발하면서 가장 자주 데이는 지점입니다. 사무실에서 되는 게 현장에서 안 되는 경우는 대체로 네트워크 때문입니다. multicast가 막힌 현장이 실제로 있었고, 네트워크 환경 차이로 설치가 실패한 적도 있습니다.

아예 인터넷이 없는 폐쇄망도 대응 범위입니다. 관리 콘솔의 「설치 USB 만들기」로 런처와 확장팩 전체를 USB에 담아 오프라인 설치할 수 있습니다.

05

모니터링

문제가 생겼을 때 추측하기 전에 열어볼 곳이 이미 있습니다. 로그와 지표가 벌써 모이고 있는데 모르면 못 씁니다.

2단 구조 — 현장에서 모으고, 클라우드엔 요약만

  • 로봇

    otel_edge가 호스트 지표와 컨테이너 로그를 모읍니다. 사이드카가 docker 이벤트 · DDS 설정 · USB · 네트워크 · 커널 로그 · GPU를 추가로 긁습니다.

  • 워크스테이션

    otel_backend가 OTLP(4317/4318)로 받아 로컬 ClickHouse에 전량 72시간 보관합니다. Grafana도 여기 있습니다.

  • 클라우드

    요약만 올라갑니다 — WARN 이상과 60초 단위 메트릭. ClickHouse와 Grafana가 전용 EC2 한 대에 같이 떠 있습니다.

원본은 현장에만 있습니다. 로봇은 클라우드로 직접 보내지 않고 반드시 워크스테이션을 거칩니다.

그래서 깊이 파야 하면 현장 ClickHouse를 봐야 합니다. MCP(:8128)로 에이전트가 직접 질의할 수 있습니다.

무엇을 어디서 보나

보고 싶은 것어디
로봇 한 대의 지표 · 로그 · 진단현장 Grafanaotel_backend 안에 들어 있습니다
버전 · 사이트 전체 현황grafana.habilis-console.comversion-monitoring 대시보드. 계정은 담당자에게
원본 데이터 직접 질의현장 ClickHouse · MCP :8128

계측하지 않는 구간이 있습니다. 고빈도 ROS 토픽(데이터 플레인)은 OTel을 걸지 않았습니다. 제어 플레인과 로봇↔클라우드 구간만 봅니다.

"로봇이 느리다"의 원인이 데이터 플레인이면 여기서는 안 보입니다. 그때는 ROS 쪽에서 직접 봐야 합니다.

GlitchTip은 아직 쓰지 않습니다. otel_backend 팩에 들어는 있지만 실제로 사용하는 단계가 아닙니다. 에러 추적도 지금은 Grafana와 로그로 합니다.

06

개발 플로우

브랜치 전략

git flow에서 develop만 빠졌다고 보면 됩니다. feature 브랜치에서 작업하고 로컬에서 테스트한 뒤 머지하고, 릴리즈 브랜치에서 다시 테스트합니다.

develop이 없는 건 상태를 따라간 결과입니다. 아직 프로덕션 단계가 아니었고, 하드웨어 의존이 커서 dev 환경을 따로 두는 의미가 크지 않았습니다.

테스트용 장비가 따로 없습니다. 제대로 확인하려면 결국 로봇이 붙은 룸에서 돌려봐야 하고, 그 자리가 곧 릴리즈 브랜치 테스트입니다.

빌드에서 디바이스까지

개발이 두 명이고 제품마다 담당이 한 명이라, 리뷰를 건너뛰면 그 코드를 본 사람이 세상에 한 명뿐이 됩니다.

특히 런처와 공통 CI는 모든 팩에 영향이 가는 지점이라, 여기만이라도 리뷰를 거는 게 비용 대비 효과가 큽니다.

배포 — 태그를 밀면 디바이스까지

확장팩 레포에 태그를 푸시하면 공용 CI가 돕니다. 빌드 결과는 OCI 형식으로 배포 서버에 올라가고, 디바이스는 그걸 번들 단위로 내려받습니다.

  • 태그 푸시

    각 팩 레포가 habilis-extension-release의 워크플로를 호출합니다. prepare → bake 두 단계로 돌고, 러너 사양(2 · 8 · 16코어)을 고를 수 있습니다.

  • 두 형식 업로드

    지금은 OCI Image Layout과 기존 oci.tar를 둘 다 올립니다. 런처가 양쪽을 다 지원해야 해서 기본값이 both입니다. Layout이 안정화되면 oci.tar를 걷어냅니다.

  • 배포 서버

    habilis_oci_server가 dl.habilis-console.com으로 내려줍니다. 확장팩뿐 아니라 런처 설치 스크립트, Intel/AMD · ARM 설치기, 설치 USB, 라이선스 파일이 전부 이 서버에서 나갑니다.

  • 콘솔 버전 번들

    디바이스가 팩 태그를 직접 고르지 않습니다. 관리 콘솔에서 팩 조합을 묶어 「콘솔 버전」을 만들고, 설치할 때 그 번들 이름을 지정합니다. 룸마다 다른 번들을 쓰는 이유가 여기 있습니다.

  • 채널

    -dev · -rc 태그는 기본 카탈로그에 뜨지 않습니다. 런처에서 experimental을 켠 곳만 받습니다. 정식 태그라야 콘솔 버전에 넣을 수 있습니다.

팩 이름을 바꾸면 새 확장팩이 됩니다. 파이프라인이 image_name으로 팩을 구분해서, 이름을 바꾸면 이어지지 않고 별개로 올라갑니다.

한 레포에 팩 하나입니다. Dockerfile 경로가 고정이라고 가정하고 짜여 있어서 모노레포로 여러 팩을 배포하는 건 아직 안 됩니다.

CI는 분 단위로 돈이 나갑니다. 큰 러너를 쓰면 빠르지만 비용이 붙고, 실제로 GitHub Actions 사용량을 다 써서 빌드가 멈춘 적이 있습니다.

07

처음 붙을 때

구조를 알았으면 그다음은 손에 쥐는 것입니다. 순서대로 하면 됩니다.

  • 01 · VPN

    사무실 wifi면 필요 없습니다. 밖에서 붙을 거면 WireGuard .conf를 플랫폼팀에 요청하세요. 사람 · 기기 단위로 발급합니다.

  • 02 · 콘솔 설치

    장비에 런처를 깝니다.
    curl -fsSL https://dl.habilis-console.com/new-launcher/install.sh | sh -s -- --version <번들명>
    번들명은 관리 콘솔에서 만든 콘솔 버전 이름입니다. 경로가 아직 new-launcher인 건 저장소 이름만 바뀐 흔적입니다.

  • 03 · 장비

    런처는 리눅스만 지원합니다. ai_manager · dataset_manager가 GPU를 요구해서 노트북에서는 정상적인 테스트가 어렵습니다.

  • 04 · 관리 콘솔

    admin.habilis-console.com에서 사용자 · 쿼터, 콘솔 버전 번들 만들기, 설치 USB를 다룹니다. VPN이나 사내망에서만 열립니다.

  • 05 · Grafana

    grafana.habilis-console.com의 version-monitoring 대시보드로 버전과 사이트 현황을 봅니다. 계정은 담당자에게 요청하세요.

  • 06 · 로봇 없이

    실물 장비가 없을 때는 habilis_robot_sim이 로봇 자리를 채웁니다. docker compose up 한 번으로 전부 뜨는 환경은 없습니다.

원격 개발 서버 접속 방법과 계정 발급 절차는 아직 문서로 없습니다. 지금은 물어보는 수밖에 없습니다.
