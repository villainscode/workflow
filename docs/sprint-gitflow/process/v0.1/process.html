Git-flow 스프린트 개발 프로세스

스프린트 한 번은 14일입니다. 1주차에 개발하고 테스트한 뒤 첫 코드 리뷰를 받고, 2주차에 QA를 거쳐 배포하고 데모합니다. 개발자는 매일 로컬에서 리뷰하고, 팀이 정한 두 시점(D7, D14)에는 CI의 리뷰 에이전트가 자동으로 리뷰해 Slack으로 알립니다.

01 · 전체 흐름

한 스프린트에서 브랜치가 움직이는 방식

원칙 1 · 티켓 먼저

Asana 티켓 없이 브랜치를 만들지 않는다

브랜치 이름, 커밋, PR 제목에 티켓 번호(WF-201)를 넣습니다. CI 리뷰 결과가 이 번호로 티켓에 연결됩니다.

원칙 2 · PR로만 머지

develop과 main은 PR로만 바뀐다

PR이 열리면 CI 리뷰 에이전트가 돌고, critical·high가 하나라도 있으면 필수 체크가 실패해 머지가 막힙니다.

원칙 3 · 리뷰는 두 층

매일은 로컬, 체크포인트는 CI

로컬 리뷰는 개발자가 매일 직접 돌립니다. 팀이 함께 보는 리뷰는 D7과 D14 두 번이고, CI가 자동으로 진행합니다.

원칙 4 · 배포는 스프린트 단위

hotfix 브랜치를 쓰지 않는다

배포는 D14에 release 브랜치로만 나갑니다. 배포 뒤 발견된 결함은 다음 스프린트 D1에 티켓으로 만들어 같은 흐름으로 고칩니다.

D10은 개발 마지막 날이면서 release 브랜치를 만들고 QA를 시작하는 날입니다. 주황색 칸이 CI 리뷰 에이전트가 도는 날입니다.

03 · 리뷰 두 층

로컬 리뷰는 개발자의 일, CI 리뷰는 팀의 관문

로컬 리뷰는 결과를 모으지도 않고 머지를 막지도 않습니다. 머지를 막는 것은 CI 리뷰뿐이고, 팀이 정한 체크포인트는 D7과 D14입니다.

로컬 · 매일 · 개발자

push 전에 스스로 거른다

Claude Code
/code-review 결함 찾기, /simplify 중복과 불필요한 복잡도 정리, /security-review 보안 점검
Codex
/review
언제
하루 작업을 push하기 전. 최소 하루 한 번
결과
개발자가 직접 고치고 커밋합니다. 따로 기록하거나 보고하지 않습니다
CI · D7 / D14 · 리뷰 에이전트

PR이 열리면 자동으로 돈다

트리거
D7 PR feature → develop, D14 PR release → main
범위
PR의 base 브랜치와 비교한 전체 변경
판정
critical·high가 있으면 필수 체크 ocr-review 실패 → 머지 차단
알림
통과와 차단 모두 Slack에 보냅니다. 차단이면 PR 작성자를 멘션하고 지적마다 ID를 붙입니다
.github/workflows/ocr-review.yml · on (OCR 가이드에서 바꿀 부분) 
# feature/** push 트리거는 빼고, develop·main으로 가는 PR에서만 돈다
on:
  pull_request:
    branches: [develop, main]
    types: [opened, synchronize, reopened]

D8–D10에 develop으로 들어가는 추가 PR도 같은 트리거로 자동 리뷰됩니다. 일정을 따로 잡지 않고 게이트만 통과하면 됩니다. bugfix → release PR은 CI 리뷰를 돌리지 않습니다. 대신 D14 리뷰가 release 전체를 다시 봅니다.

04 · 일정별 진행

D1부터 D14까지 할 일

  1. D1플래닝

    스프린트 목표와 범위를 정하고, Asana에 릴리즈 태스크(v2.4.0)와 기능 티켓을 만듭니다. 각자 develop에서 feature 브랜치를 만듭니다.

    terminal · 각자 
    git switch develop && git pull
git switch -c feature/WF-201-login-lock
  2. D2–D6개발 · 테스트

    feature 브랜치에서 개발합니다. push하기 전에 로컬 리뷰를 돌리고 나온 문제를 고칩니다. feature 브랜치에 push해도 CI 리뷰는 돌지 않습니다.

    매일 · push 전 
    # Claude Code
/code-review
/simplify
/security-review
# Codex
/review

git commit -am "feat(auth): 로그인 5회 실패 시 계정 잠금 [WF-201]"
git push -u origin feature/WF-201-login-lock

    D6에는 새 기능을 넣지 않습니다. 단위·통합 테스트를 채우고, develop 최신 내용을 받아 충돌을 미리 풉니다.

  3. D7코드 리뷰 ①

    develop으로 PR을 엽니다. CI 리뷰 에이전트가 자동으로 돌고 결과를 Slack으로 보냅니다.

    terminal 
    gh pr create --base develop --title "WF-201 로그인 5회 실패 시 계정 잠금" \
  --body "Asana: https://app.asana.com/... (WF-201)"
    • 통과: 동료 1명의 승인을 받고 squash 머지합니다. Asana 티켓을 “develop 반영”으로 옮깁니다.
    • 차단: 같은 브랜치에서 고쳐 push하면 리뷰가 다시 돕니다. 오탐이면 /ocr-triage <id> false_positive "사유"를 남기고 테크 리드가 머지 여부를 정합니다.
    • medium 이하는 머지를 막지 않습니다. 이번에 고치거나 D8에 처리할 티켓으로 남깁니다.
  4. D8–D10마무리 · 동결

    D7 리뷰에서 남은 지적과 남은 개발을 끝냅니다. 이 PR들도 develop 게이트를 그대로 통과해야 합니다. D10 오후에 기능을 동결하고 테크 리드가 release 브랜치를 만듭니다. 이때부터 develop에는 다음 스프린트 작업이 들어가도 됩니다.

    terminal · D10 테크 리드 
    git switch develop && git pull
git switch -c release/2.4.0
./scripts/bump_version.sh 2.4.0
git commit -am "chore(release): 버전 2.4.0"
git push -u origin release/2.4.0
  5. D11–D13QA

    release 빌드로 QA를 합니다. 버그는 Asana에 티켓으로 만들고, develop이 아니라 release에서 bugfix 브랜치를 땁니다. 고친 내용은 D14에 release가 develop으로 돌아갈 때 함께 들어갑니다.

    terminal · 담당자 
    git switch release/2.4.0 && git pull
git switch -c bugfix/WF-209-csv-bom
# 로컬 리뷰 후
gh pr create --base release/2.4.0 --title "WF-209 CSV 한글 깨짐"

    D13에 QA를 끝내고 배포 여부를 정합니다. 해결되지 않은 critical 버그가 있으면 그 기능을 이번 배포에서 뺄지 이때 결정합니다.

  6. D14코드 리뷰 ② · 배포

    release → main PR을 열면 CI 리뷰 에이전트가 main과 비교해 이번 릴리즈 전체를 리뷰하고 Slack으로 알립니다.

    • 통과: release → main, release → develop 두 PR을 merge commit으로 머지합니다(squash 금지). main에 v2.4.0 태그를 붙여 배포한 뒤 release 브랜치를 지웁니다.
    • 차단: release에서 bugfix로 고치고 다시 리뷰받습니다. 그날 안에 해결되지 않으면 테크 리드가 배포를 미루거나 해당 기능을 빼고 배포합니다.
    • 배포 후 데모와 회고를 합니다. 남은 지적과 배포 후 결함은 다음 스프린트 백로그로 넘깁니다.
    terminal · 테크 리드 (두 PR 머지 후) 
    git switch main && git pull
git tag -a v2.4.0 -m "v2.4.0"
git push origin v2.4.0
git push origin --delete release/2.4.0

06 · 완료 기준

다음 단계로 넘어가기 전에 확인할 것

D1 → 개발 시작

  • 모든 작업에 Asana 티켓과 담당자가 있다
  • 브랜치 이름에 티켓 번호가 있다

D7 → develop 머지

  • D6에 테스트를 채웠고 develop과 충돌이 없다
  • ocr-review 체크가 통과했다
  • 차단됐던 지적은 고쳤거나 오탐 판정을 남겼다
  • 동료 1명이 승인했다

D10 → release 생성

  • 릴리즈 태스크의 티켓이 모두 develop에 머지되었다
  • D7 리뷰에서 넘긴 지적이 처리되었거나 다음 스프린트 티켓이 되었다

D14 → 배포

  • QA 버그가 모두 bugfix PR로 release에 들어갔다
  • main PR의 ocr-review 체크가 통과했다
  • main과 develop 두 PR 모두 merge commit으로 머지했다
  • 태그를 붙이고 배포했다. 데모와 회고를 마쳤다

워크플로 설치, Slack Webhook, Ruleset은 OCR 리뷰 게이트 운영 가이드를 따르고, CI 리뷰를 API 키와 Max 구독 중 어느 쪽으로 돌릴지는 리뷰 방식 비교를 따릅니다.

이 문서에서 뺀 것: hotfix 브랜치, 고객사별 라이선스와 패키지, 리뷰 원장과 골든셋 구성. 판정(/ocr-triage) 수집과 골든셋 설정은 별도 문서로 정리할 예정입니다.
